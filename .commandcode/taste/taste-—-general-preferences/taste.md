# Taste — general preferences
- Never present an inference as fact: distinguish clearly between what was actually observed, what is not confirmed, and what is inferred (e.g. explicit OBSERVED / NOT CONFIRMED / INFERRED labeling). Confidence: 0.85
- Prefer an explicit unconfirmed/unknown marker over guessing; the user repeatedly states "do not guess" and "if something was not observed, mark it NOT CONFIRMED". Confidence: 0.85
- Do not invent data or values (e.g. medical/reference ranges). Missing values are reported as blank/unconfirmed rather than filled in or normalized. Confidence: 0.75
- Research and document the actual behavior first, then implement: read the reference/source material, inspect the current implementation read-only, produce a gap analysis, and only then change code. Confidence: 0.75
- Prefers minimal, surgical changes: only touch modules in scope and never modify unrelated pages, components, or APIs; if a shared dependency must change, make the smallest safe change and explain why. Confidence: 0.8
- When UI already exists, implement functionality only — do not redesign or change layout unless a functional requirement absolutely requires it. Confidence: 0.8
- Does not want data mutated silently: compare and reconcile before any import/overwrite, report matches/missing/extras, never delete or overwrite existing records without a reconciliation report. Confidence: 0.7
- Treat external/reference systems as strictly read-only: do not exercise create/update/delete/approve-type actions to "test"; use existing records only. Confidence: 0.75
- Never persist credentials or session/authentication material into project files, logs, or saved sessions. Confidence: 0.8
- Prefers verification with evidence rather than claiming success: run the project's existing check commands (backend typecheck, frontend tests, and the production build where practical) and exercise the running local instance end-to-end, cleaning up any temporary test data afterwards. Confidence: 0.75
- Wants important configuration stored structurally in the model/database, not only as display text. Confidence: 0.7
- Prefers business/domain logic to be backend-authoritative: the frontend should not independently calculate domain values (e.g. medical/reference ranges), only display or preview what the backend returns. Confidence: 0.75
- Before modifying code, state the exact files to be changed and the functional change each will receive. Confidence: 0.7
- Prefer extending/reusing existing models and schema over creating duplicate models when one already represents the relationship. Confidence: 0.7
- When existing code already implements a required behavior correctly, leave it unchanged and report it as already implemented rather than rewriting it. Confidence: 0.7
- A feature is only "implemented" once actual data flows end-to-end (source system value → database → API → UI → result screen); the mere existence of the schema, model, or API endpoint does not count as parity. Confidence: 0.8
- When the reference/source system does not provide enough evidence for a rule (priority, fallback, semantics), leave the existing project behavior unchanged and document it rather than inventing a policy. Confidence: 0.7
- Reproduce values from the authoritative source system itself rather than inferring or converting them (e.g. do not derive structured mappings from displayed text or general domain knowledge). Confidence: 0.7
- Avoid dynamic code execution: no `eval` or executing formula/logic strings. Prefer explicit, type-safe, named definitions (e.g. a formula registry) that are individually testable. Confidence: 0.7
- Keep reusable logic in dedicated helper modules with unit tests rather than scattering it through UI/component code. Confidence: 0.65
- Resolve cross-entity dependencies/relationships by stable identity (IDs, or normalized names as a controlled fallback) rather than positional order (row numbers) or loose substring matching that could select the wrong record. Confidence: 0.6
- Handle edge cases explicitly with clear user-facing messages (missing inputs, division by zero) instead of producing NaN/Infinity or persisting invalid values. Confidence: 0.6
- Treat user-supplied assets (logos, images, documents) as the source of truth: use them as-is, never recreate, crop out, or duplicate their content (e.g. don't re-add text already inside a supplied logo), and never edit the source file — control only display size/container from the UI. Confidence: 0.7
- When resizing images, preserve the original aspect ratio and avoid cropping, stretching, or distortion (use `object-fit: contain` or the project equivalent). Confidence: 0.65
- Keep each supplied asset in its designated location; do not substitute one asset for another's (e.g. header logo vs sidebar logo stay distinct). Confidence: 0.55
- When removing a UI element, remove it completely — including its wrapper/container, its reserved height/blank space, and any now-unused imports — rather than hiding it or leaving an empty placeholder. Confidence: 0.6
- Dislikes empty vertical space and oversized UI chrome; prefers compact, space-efficient layouts where content (e.g. navigation items) starts immediately with no unused gaps. Confidence: 0.6
- Before writing any code, always inspect the existing project end-to-end (entry point, routes, controllers, services, models, middleware, env/config, DB connection) and follow its current architecture and conventions; never spin up a new/parallel project or backend and never restructure existing code unnecessarily. Confidence: 0.85
- Do not install unnecessary packages; if a new dependency is genuinely required, explain why before installing it (prefer the language's built-ins/stdlib). Confidence: 0.85
- Keep secrets strictly server-side: never hardcode them, never expose via public/client env vars (e.g. NEXT_PUBLIC_*), never place tokens/secrets in frontend code, and never commit .env files. Confidence: 0.8
- In medical/LIS contexts, never log, print, or publicly expose patient/report content or other sensitive PII unnecessarily. Confidence: 0.75
- After implementing, provide a concrete handoff: files created/modified, exact commands to run and test it locally, required env variables, packages added, and any issues found in the existing code that could block it. Confidence: 0.7
- For risky/live data operations (migrations, restores, copies), insists on strict guardrails: non-destructive only (never use destructive flags like `--drop` or drop operations), target the namespace/database explicitly and unambiguously, and leave adjacent/untouched resources (other databases) and the source data intact. Confidence: 0.7
- Expects write/restore operations to be verified afterwards with read-only checks comparing the result against the source/backup (collection names, per-collection document counts, totals), reporting any missing/extra/mismatched items. Confidence: 0.7
- Gates deployment/production steps behind explicit instruction: keep changes local and verify them against the running local instance first, and do not deploy (e.g. to Cloudflare) or take irreversible steps until the user explicitly says so. Confidence: 0.7
- Treat production diagnosis as strictly read-only: no inserts/updates/deletes, no password resets, no user creation/deletion, no seeding or migration of the production database until the user explicitly approves it — inspect data read-only and report the finding instead of "fixing" it. Confidence: 0.75
- When temporary diagnostic instrumentation is needed, it must be clearly marked in code (e.g. a commented block naming the issue it diagnoses and noting it should be removed afterwards) and must log only safe non-sensitive facts (existence flags, active flag, non-sensitive role, password-match boolean) — never the submitted password, stored hash, token, cookie, or connection string. Confidence: 0.7
- Prefers a concise, structured end-of-task report limited to the fields that were requested (e.g. PASS/FAIL, target database, collection count, total document count, users count, mismatches/errors) rather than a verbose narrative; audit/config tasks often come with an explicit lettered schema (A. Files changed, B. What was fixed, C. current URL, …) that should be followed, with anything unconfirmable marked "NOT VERIFIED". Confidence: 0.7
- Never asks to be prompted for secrets/credentials (API tokens, MongoDB passwords, JWT secrets, WhatsApp tokens): work from variable names, existing placeholders, and documented config instead, and never print or expose secret values. Confidence: 0.8
- For a production backend, prefers a long-running Node host (e.g. Render running `node dist/server.js`) over serverless/edge runtimes; explicitly rejects Cloudflare Workers for an Express + Mongoose app because the Mongoose model layer is incompatible with per-request I/O isolation. Confidence: 0.7
- Prefers a single centralized API base URL / config point (one API client reading one env var) instead of repeating the backend URL or endpoint logic across many files. Confidence: 0.7
- Wants environment-driven configuration for production with safe local defaults — port from `process.env.PORT` (local fallback), CORS allow-list from env, cookie/session settings from env, explicit database name — rather than values hardcoded for production. Confidence: 0.7
- Keeps env files out of git while shipping a committed `.env.example` containing variable NAMES and safe placeholders only; expects `.gitignore` to cover `.env`, `.env.*`, with `!.env.example` retained so the example can be committed. Confidence: 0.7
- When adding a new runtime/deployment target (e.g. Cloudflare Workers) to an existing backend, do it additively: keep the existing Node entry point and the current local dev command (e.g. `npm run dev`) working unchanged, and add a separate entry point for the new runtime rather than replacing `src/server.ts`. Confidence: 0.7
- When porting to a new runtime/host, verify real runtime compatibility empirically (actually run the target runtime locally against realistic requests) rather than assuming it works; if a fundamental incompatibility surfaces, stop and report the exact issue and options instead of unilaterally changing the architecture (e.g. swapping out the database layer). Confidence: 0.75
- Prefers current, officially supported tooling and platform approaches (e.g. an up-to-date compatibility date and the currently documented integration method) over outdated or legacy patterns. Confidence: 0.6
- Prefers CORS configured as an explicit, configurable allow-list (e.g. a production-origin env var) rather than an insecure wildcard, while still allowing credentials. Confidence: 0.6
- Fix the root cause inside the existing mechanism instead of adding a parallel workaround; explicitly rejects redundant additions when the existing machinery already handles the case correctly (e.g. do not add a separate OPTIONS route when the existing CORS middleware already answers preflight). Confidence: 0.7
- Origin/allow-list values must be bare origins — scheme + host (+ port), never a path, `/login`, or trailing slash — and the code should be tolerant of messy entries (normalise and de-duplicate) so sloppy config does not silently block requests. Confidence: 0.65
- When the task is diagnosis, makes no behavior-affecting change: restricts edits to clearly-marked temporary safe diagnostics, leaves the actual fix unapplied even when the cause is already identified, and waits for explicit approval before implementing it. Confidence: 0.75
- For cross-site credentialed auth, expects the session cookie to be `HttpOnly` + `Secure` + `SameSite=None` with `Path=/` and no `Domain` attribute; treats `SameSite=Lax` as wrong for that flow. Confidence: 0.65
- When disabling/removing a broken mechanism, remove ONLY that mechanism and never drop the guarantee it provided: keep the protection enforced through the existing sanctioned path and verify the coverage is preserved (e.g. delete the middleware cookie check but confirm the `/auth/me`-based guard covers every protected route). Confidence: 0.7
